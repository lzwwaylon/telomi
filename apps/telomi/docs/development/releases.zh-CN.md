# 分支与发布

[English](releases.md) | 简体中文

功能分支 → dev → 发布验收 → main → Tag / Release

## 分支职责

| 分支 | 来源与用途 | 合并目标 |
|---|---|---|
| `feat/*`、`fix/*`、`chore/*` | 从 `dev` 创建，一个独立功能、修复或维护任务 | `dev` |
| `dev` | 日常集成分支，也是仓库默认分支 | 验收通过后合入 `main` |
| `main` | 已通过发布验收的稳定代码 | 用 Tag 标记正式版本 |
| `hotfix/*` | 从 `main` 创建，修复已发布版本的紧急问题 | 验收后合入 `main`，再同步回 `dev` |

功能分支可持续提交和推送。普通 PR 向 `dev` 提交；PR 中说明问题、最终行为、验证结果和限制。默认使用 merge commit 合并，保留可追溯的分支祖先关系；长期分支之间不使用 squash 或 rebase 合并。

## 发布验收

1. 创建 `dev → main` 的发布 PR，说明拟发布版本、兼容性变化和发布范围。
2. 对 PR 的当前提交完成[本地确定性检查](testing.md#submission-checks)、相关用户流程的[真实 E2E](e2e.md)，以及适用的[产品行为验证](attestation.md)。影响验证结果的新提交需要重新检查。
3. 完成下述安装与升级验收，在 PR 中记录来源/目标 SHA、平台、结果和限制。
4. 维护者确认验收证据后合并到 `main`；确认合并后的文件树与已验证版本一致，否则补做受影响的检查。
5. 在这个确定的 `main` 提交上创建版本 Tag（例如 `v0.0.1`），再创建对应 GitHub Release。记录变更、升级要求和已知限制，发布需要的产物。
6. 将 `main` 的合并结果同步回 `dev`，保持两条长期分支的祖先关系。已发布的 Tag 不移动；修复通过新补丁版本发布。

普通用户使用最新正式 Release；参与开发时使用 `dev`。

## 安装与升级验收

- 首个版本：在没有维护者私人配置、现有数据或共享虚拟环境的干净 checkout
  按 README 安装、构建和启动；通过真实页面验证配置及关键用户流程。
  记录实际验证的平台，不把未测平台声明为已支持。
- 后续版本：在隔离环境安装上一正式版本，用非敏感样本建立 Goal、报告、Wiki
  和长期记忆，按[升级与恢复](../upgrading.zh-CN.md)备份，再升级到候选版本。
  验证数据可读、凭据和配置保留、关键流程仍可完成。更旧版本是否可直升，
  由 Release 明确说明，不凭推测承诺。
- 有数据/配置迁移时，实际演练从对应备份恢复旧版本，记录恢复范围与可能丢失
  的升级后数据。未验证的恢复路径不能标为可回滚。
- 安装/升级检查属于发布验收，不要求每个普通文档 PR 重做，也不以确定性测试
  通过替代真实安装与用户流程验证。

每次 Release 说明至少包含：准确版本及提交、用户可见变化、升级步骤、
配置/数据兼容性与备份恢复要求、已知限制和验证平台。首次发布注明无旧公开版本
需要迁移；后续版本保留连续历史，已发布 Tag 不移动。

## 紧急修复

从 `main` 创建 `hotfix/*`，经 PR、适用检查和验收后合回 `main`，发布补丁 Tag/Release。随后通过 `main → dev` 的同步 PR 带回修复，避免后续版本重新引入问题。

## GitHub 仓库设置

仓库创建后由维护者设置：

- 默认分支为 `dev`，普通 PR 面向 `dev`。
- `dev`、`main` 均要求通过 PR 合并、[本地检查通过](testing.md#submission-checks)并解决审阅意见；禁止强制推送和删除长期分支。
- 云端 Actions 启用时，将 CI 任务 `tests (1/3)`、`tests (2/3)`、`tests (3/3)` 和 `typecheck, build and contracts` 设为必需检查；停用期间不设必需检查。审查人数按实际维护团队设置。
- 保留 merge commit 合并方式，与上述长期分支同步约定一致。

这些远端设置独立于仓库文件，CI 配置本身不等于分支保护已启用。私有仓库可用的强制保护功能取决于 GitHub 套餐。
